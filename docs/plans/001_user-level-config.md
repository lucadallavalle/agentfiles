# 001: User-level config

## Overview

ROADMAP step 3: the first CLI command, `agentfiles doctor` / `doctor --fix`. It merges the shipped user-level config (instructions, permissions, preferences) into Claude Code, Codex and OpenCode without clobbering local edits, and reports drift. Bootstrap, repo setup and repo drift come in step 4.

## Technical Approach

The CLI (`src/cli/`) parses arguments only. `src/core/` reads `config/`, keeps the state file and decides per tracked entry: missing, in sync, drifted (edited) or no longer shipped. Each adapter maps the neutral config onto its harness's files and key shapes and edits them in place, keeping comments and formatting. Mechanism, content and paths are settled in the decision log; this plan only adds the order and the open points below.

### Open questions (for the grill)

- **Q1 CLI distribution.** No install script means `npx github:` can't compile, and Node doesn't strip types under `node_modules` (confirm in C01). Options: (a) a committed single-file bundle, checked for staleness by the gate like the manifests, so the package keeps no runtime dependencies; (b) runtime `dependencies` plus committed `tsc` output, installed by `npx` and maybe by `opencode plugin add`.
- **Q2 TOML editing.** smol-toml (D8) drops comments when it stringifies; the decision log requires edits that keep them. Codex's only tracked key is the top-level `developer_instructions` (permissions are a tracked rules file). Options: smol-toml to read plus a text splice of top-level keys; a comment-preserving TOML library (a D8 deviation, logged).
- **Q3 Array keys.** Claude Code `permissions.allow`, OpenCode `instructions` and OpenCode permission rules are shared with the user and the harness. Track each element we add, or the whole key? Where do our OpenCode rules go, given last match wins?
- **Q4 `doctor` result.** Output format and exit codes: non-zero on drift? After `--fix`, when edited entries remain?
- **Q5 Missing harness and moved homes.** Skip a harness whose config directory is absent, or create it? Honor `CLAUDE_CONFIG_DIR`, `CODEX_HOME`, `XDG_CONFIG_HOME`, `XDG_STATE_HOME`?
- **Q6 Instructions copy.** Is `~/.config/agentfiles/instructions.md` a tracked file (updated by `--fix` while unedited), or copied once and left alone?
- **Q7 spiral-review dependencies.** Do they block any chunk, or only step 4's `bootstrap`?

## Implementation

`doctor` without `--fix` never writes. `--fix` writes missing or unchanged-but-outdated entries, removes unshipped ones only if unchanged, and reports edited ones. Every run is idempotent.

## Testing Strategy

- Unit: drift states per entry kind (file, JSON key, TOML key, array element per Q3); removal of unshipped entries; idempotency (`--fix` twice changes nothing).
- Fake home: every test runs the CLI with `HOME` and the env vars from Q5 pointing at a temp directory. Fixtures with comments, reformatted files and foreign keys must survive untouched.
- Real harnesses, as PR evidence like step 2: C01 `npx github:…#<branch> doctor` and `opencode plugin add github:…#<branch>`; C02–C04 each harness loading the shipped instructions and a permission rule against a fake home (C03: a rule from `rules/agentfiles.rules` applies alongside `default.rules`).

## Acceptance Criteria

- `agentfiles doctor --fix` on a fake home with all three harnesses writes the shipped config; a second run changes nothing; `doctor` then reports no drift.
- Editing a tracked entry makes `doctor` report it and `--fix` leave it alone.
- No literal secret can enter `config/` without failing the gate.
- All tests passing
